# HTTP control endpoint reservations

HTTP execution can receive trusted infrastructure TCP endpoint reservations through host-owned execution configuration. Each reservation binds one port to a bounded list of literal IPv4/IPv6 addresses. The address and port pair is rejected during policy construction even when a different hostname alias or trusted non-public mapping resolves to it. Resolver and network-service boundaries each snapshot and validate their own configuration; later mutation by a caller cannot loosen a constructed service.

The strict private `broker-daemon.json` loader accepts an optional `reservedControlEndpoints` field and forwards its validated, frozen value to the broker host. Omission means an empty list; explicit `null` and malformed entries are rejected. The app client validates but does not expose this field, and execution plans and grant requests cannot override it. This makes trusted private manifest configuration usable by a future installer, but the manifest has no live listener acknowledgement, enrollment authority, or production tuple source today. File ownership/modes are not process authentication against another process running as the same user.

The proxy firewall emits an exact destination-address and TCP-destination-port drop for each reserved tuple before established-connection and target-allow rules. Kernel verification requires those exact drops as a contiguous output-chain prefix, with no earlier routing or match rule that could bypass them. The network service also rejects a matching execution policy before Docker provisioning.

Reservations default to an empty list. No companion endpoint is active or claimed by this change; production wiring must provide the actual trusted endpoint tuple before a companion listener is enabled. Existing public HTTP execution retains its current behavior while the list is empty. The OrbStack qualification can use its synthetic host-side receiver to verify a configured denial and a separate positive control; unit tests do not establish that a production endpoint is installed or reachable. Docker Desktop qualification remains separate.

The OrbStack ARM64 qualification passed all 15 checks, including one positive control and zero requests to the configured IPv4 host-mapped reserved tuple, with the corresponding kernel DROP verified in both the regular execution and private-broker path. Its DNS and unauthorized-IPv6 checks are baseline isolation checks, not evidence for an IPv6 reservation. The captured [qualification evidence](../../infrastructure/isolation/evidence/orbstack-companion-control-reservation-arm64.json) records the OrbStack engine and exact image IDs; it does not establish production companion activation or Docker Desktop behavior.
