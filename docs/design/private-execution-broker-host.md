# Private execution broker host

This is another incremental part of [#161](https://github.com/olekgolus11/nulltrace/issues/161). `ExecutionBrokerHostService` assembles the public HTTP supervisor, recovery, receipt journal, installation lock and authenticated broker handler, then listens on a Unix socket. This is a host component for a future dedicated broker process, not a TUI integration or a distribution-ready daemon.

`ExecutionBrokerInstallationService` provisions the stable local identity for a trusted installer. Given an absolute private data path and a trusted stable installation ID, it creates a `0700` directory, a random 32-byte HMAC key, distinct random 64-character lowercase-hex client and administrator tokens, and a `0600` SQLite receipt journal keyed with the existing installation marker. Files use exclusive creation, are synced before success, and are checked for owner, mode, link count and path identity. A private lock serializes provisioners. Repeated provisioning returns the existing credentials only after verifying the keyed journal. Existing partial state, stale locks, symlinks, hard links, unexpected SQLite sidecars, wrong ownership, wrong modes and a journal keyed to another identity fail closed; credentials are never replaced. A valid legacy installation can gain its missing administrator token only after the existing key, client token and keyed journal are verified. A crash that leaves partial state requires explicit operator recovery after inspection.

The service returns the credentials only to its trusted caller in memory; it does not put them in arguments, environment variables or logs. The caller must handle the HMAC key and administrator token as secrets, and clear the key buffer when finished. The key, tokens and database are protected from other local users by POSIX ownership and permissions. On Docker Desktop or OrbStack, where NullTrace and its broker share the operator's macOS account, these files and sockets do not form an independent privilege boundary: same-user software can read the administrator token and access both broker channels and the desktop engine socket. A separate low-privilege OS identity and production service installation remain deployment work.

The provisioning lock is removed only by the process that created it and only if its inode is unchanged. If the process crashes, the leftover lock is deliberately not cleared automatically. An operator or installer must first verify that no broker is using the directory, inspect the key, token and journal for a complete matching installation, then explicitly remove the stale lock or discard and reprovision the entire installation after deciding that its receipts can be lost. Wrong-mode, replaced or partial managed paths are never repaired in place. The installation service does not change permissions on pre-existing resources.

Startup still refuses a missing, replaced, wrong-key or wrongly permissioned journal, and never creates a replacement receipt journal. The HMAC key, bearer identity, approved profiles, image IDs and authorization lookup are supplied by trusted infrastructure; operator/model data cannot supply Docker options. The provisioning service does not create a daemon approval manifest or wire operator approvals to the process.

Startup acquires the exclusive installation lock before touching stale sockets or engine resources, opens the existing journal, verifies its keyed installation marker, reconciles installation-owned containers and networks, and only then starts the Unix listeners. Execution and grant issuance use separate sockets (`broker.sock` and `broker-admin.sock`), each created under a restrictive umask and set to mode `0600`. Grant requests require the distinct administrator token, a bounded strict schema, the broker's public cURL profile validator, and an expiry within fifteen minutes; duplicate grant IDs fail with conflict. The execution bearer cannot use the administrative socket, and the execution socket has no grant route. Another live host cannot remove the first host's sockets. Shutdown stops admission on both channels, drains in-flight requests, cancels active supervised runs, reconciles resources, closes the journal, removes owned sockets and releases the lock. An uncertain cleanup still fails closed on the next startup.

Tests use a real Unix socket and verify authenticated admission, owner permissions, single-host exclusion, missing/replaced journal rejection, orphan recovery before admission, unavailable-engine rejection and request draining. The unit-test Docker adapter only simulates empty resource inventory. The OrbStack ARM64 qualification also submits one approved public cURL plan through this host's Unix socket, observes one request at the approved receiver, receives the bounded response event and waits for confirmed cleanup. Its controlled resolver maps only `approved.test` to the test receiver; this is trusted test infrastructure, not a client-selected DNS override. The existing forbidden receiver still observes zero requests for redirect and direct-bypass probes. See the recorded evidence under `infrastructure/isolation/evidence/`.

`infrastructure/isolation/run-broker.ts` runs this host in a dedicated process. It reads the HMAC key, client token and separate administrator token from private files under the broker-owned `0700` directory, alongside a bounded `broker-daemon.json` manifest. These values are not passed through argv or environment. The manifest has exact fields for installation and instance IDs, an absolute Docker executable path, immutable image IDs and trusted target mappings; grants arrive only through the separate administrative socket. The daemon retains the restricted GET-only `public-curl-v1` profile and adds a separate `public-curl-worker-v1` profile with fixed Bun argv and a bounded private data slot. Public TUI cURL requests now use this worker profile through the administrative grant socket and authenticated execution socket. Authenticated cURL remains unavailable in this slice and fails with an explicit message before grant issuance. Missing or invalid broker configuration fails closed; cURL never reaches the host command runner. The worker profile binds its approved origin and fixed plan, while per-run request bytes remain a private data input and are not represented as a content-bound grant.

OrbStack ARM64 qualification starts this separate process with a minimal test environment. One approved cURL worker request reaches the controlled receiver, returns redacted output and ends with confirmed cleanup. Unit tests also verify grant admission and socket removal on SIGTERM. This proves process separation for the tested path; it does not establish a separate OS identity or prevent a same-user desktop process from opening the Docker socket itself. The application reads only `NULLTRACE_EXECUTION_BROKER_DIR`, the private directory path; it validates the client token, administrator token and manifest identity without loading the daemon HMAC key or image policy. A trusted installer must provision the broker directory, immutable image IDs, daemon manifest and live broker process before cURL is available. The current tree has no end-user broker-install command yet, so packaging must supply that provisioning and startup step. The existing authentication toggle remains visible, but selecting it reports that authenticated cURL is unavailable; no host fallback occurs. Public cURL history retains redacted logs and repository-generated `output_summary`, with no raw response artifact.

The separate application qualification drives the registered cURL tool through `ToolRunnerService` and the real session repository. Its six OrbStack ARM64 checks cover successful request delivery and redacted durable history, missing-broker fail-closed behavior, redirect denial after one approved request, cancellation cleanup and the host-runner boundary. The sanitized evidence is `infrastructure/isolation/evidence/orbstack-curl-application-arm64.json`.
