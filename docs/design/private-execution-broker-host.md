# Private execution broker host

This is another incremental part of [#161](https://github.com/olekgolus11/nulltrace/issues/161). `ExecutionBrokerHostService` assembles the public HTTP supervisor, recovery, receipt journal, installation lock and authenticated broker handler, then listens on a Unix socket. This is a host component for a future dedicated broker process, not a TUI integration or a distribution-ready daemon.

`ExecutionBrokerInstallationService` provisions the stable local identity for a trusted installer. Given an absolute private data path and a trusted stable installation ID, it creates a `0700` directory, a random 32-byte HMAC key, a random 64-character lowercase-hex client token and a `0600` SQLite receipt journal keyed with the existing installation marker. Files use exclusive creation, are synced before success, and are checked for owner, mode, link count and path identity. A private lock serializes provisioners. Repeated provisioning returns the existing credentials only after verifying the keyed journal. Existing partial state, stale locks, symlinks, hard links, unexpected SQLite sidecars, wrong ownership, wrong modes and a journal keyed to another identity fail closed; the service never replaces them or silently rotates credentials. A crash that leaves partial state requires explicit operator recovery after inspection.

The service returns the key and token only to its trusted caller in memory; it does not put either in arguments, environment variables or logs. The caller must handle the returned HMAC key as a secret and clear its byte buffer when finished. The key, token and database are protected from other local users by POSIX ownership and permissions. On Docker Desktop or OrbStack, where NullTrace and its broker share the operator's macOS account, those files are not an independent privilege boundary: same-user software can still read or replace them and access the desktop engine socket. A separate low-privilege OS identity and production service installation remain deployment work.

The provisioning lock is removed only by the process that created it and only if its inode is unchanged. If the process crashes, the leftover lock is deliberately not cleared automatically. An operator or installer must first verify that no broker is using the directory, inspect the key, token and journal for a complete matching installation, then explicitly remove the stale lock or discard and reprovision the entire installation after deciding that its receipts can be lost. Wrong-mode, replaced or partial managed paths are never repaired in place. The installation service does not change permissions on pre-existing resources.

Startup still refuses a missing, replaced, wrong-key or wrongly permissioned journal, and never creates a replacement receipt journal. The HMAC key, bearer identity, approved profiles, image IDs and authorization lookup are supplied by trusted infrastructure; operator/model data cannot supply Docker options. The provisioning service does not create a daemon approval manifest or wire operator approvals to the process.

Startup acquires the exclusive installation lock before touching a stale socket or engine resources, opens the existing journal, verifies its keyed installation marker, reconciles installation-owned containers and networks, and only then starts the Unix listener. The socket is created under a restrictive umask and set to mode `0600`. Another live host cannot remove the first host's socket. Shutdown stops admission, drains in-flight requests, cancels active supervised runs, reconciles resources, closes the journal, removes the owned socket and releases the lock. An uncertain cleanup still fails closed on the next startup.

Tests use a real Unix socket and verify authenticated admission, owner permissions, single-host exclusion, missing/replaced journal rejection, orphan recovery before admission, unavailable-engine rejection and request draining. The unit-test Docker adapter only simulates empty resource inventory. The OrbStack ARM64 qualification also submits one approved public cURL plan through this host's Unix socket, observes one request at the approved receiver, receives the bounded response event and waits for confirmed cleanup. Its controlled resolver maps only `approved.test` to the test receiver; this is trusted test infrastructure, not a client-selected DNS override. The existing forbidden receiver still observes zero requests for redirect and direct-bypass probes. See the recorded evidence under `infrastructure/isolation/evidence/`.

`infrastructure/isolation/run-broker.ts` now runs this host in a dedicated process for one pre-approved public cURL plan. It reads a 32-byte key from `broker.key`, a 64-character hex client token from `client.token`, and a bounded `broker-daemon.json` manifest, all under the broker-owned `0700` directory with mode `0600`. These values are not passed through argv or environment. The manifest has exact fields for installation and instance IDs, an absolute Docker executable path, immutable image IDs, trusted target mappings, the exact approved plan and its expiry. The daemon uses a fixed public cURL profile and a restricted GET-only argument form; this is an initial qualification profile, not a replacement for the application's full cURL feature. It never creates missing files or a missing receipt journal. Signals close the listener and wait for cleanup before process exit.

OrbStack ARM64 qualification now starts this separate process with a minimal test environment. One approved request reaches the controlled receiver, produces a broker event and ends with confirmed cleanup. A unit test also verifies socket removal on SIGTERM. This proves process separation for the tested path; it does not establish a separate OS identity or prevent a same-user desktop process from opening the Docker socket itself. Docker Desktop, production service-manager packaging, durable operator-approval delivery, authenticated requests, artifact import and TUI migration remain pending. The TUI currently retains its legacy unisolated command path.
