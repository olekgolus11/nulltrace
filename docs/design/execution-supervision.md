# Execution supervision and recovery foundation

This is an incremental implementation of [#161](https://github.com/olekgolus11/nulltrace/issues/161). It establishes cancellation, finite ownership and execution deadlines, installation-scoped recovery and a durable nonsecret outcome summary. It does not activate a tool migration or complete #161.

`HttpExecutionSupervisorService` implements the broker's existing runtime adapter for public HTTP plans with no input slots. It starts one run at a time, maintains an absolute deadline and a shorter renewable ownership lease, and passes one cancellation signal through resolution and the Docker execution boundary. The lease cannot extend the absolute deadline. An ordinary completion, cancellation, lease expiry or timeout is not considered clean until the worker and proxy environment has been removed. Failed cleanup blocks another start. Its memory-held result is intentionally only a bounded status and exit code; raw command output is not replayed by this service.

`HttpExecutionNetworkService` now requires an `ExecutionBrokerOwnershipLock`. The trusted broker must hold the `ExecutionBrokerLockService` on a private, stable installation path for its lifetime. This SQLite lock prevents a second live broker from reconciling the first one's engine resources. Every disposable container and network carries a trusted installation label. On startup the network service removes and verifies only resources with that label before starting another run. If the engine cannot be inspected or cleanup is uncertain, the backend remains locked until an explicit retry succeeds.

The broker receipt journal stores a separate outcome row containing only execution ID, terminal cause, exit code and cleanup condition. `ExecutionReceiptRepository.recordOutcome` commits the outcome with the cleanup receipt atomically. `ExecutionRecoveryService` confirms receipts only after installation-owned resources are absent. The `onSettled` callback must be wired to the receipt repository by the broker bootstrap. A failed callback blocks another run until settlement is retried. These records contain no command, URL, stdout, stderr, proxy log or secret.

The OrbStack ARM64 qualification now also creates a controlled orphan network and proves it is removed before the allowed request. It holds a real request open, cancels the running worker, and checks that execution-labeled container and network counts are zero. It reads the worker's effective cgroup and file-size limits, then actively tests memory exhaustion, process creation denial and an oversized file write. All three runs confirm environment cleanup. The current run uses 128 MiB memory, 48 processes and an 8 MiB individual-file cap; these are qualification values, not a claim that every operator plan should use them.

Remaining #161 work includes production key/identity provisioning and a live operator-approval feed for the dedicated broker daemon, hostile artifact collection and application persistence, active CPU throttling tests, cancellation and restart tests across all lifecycle phases, and Docker Desktop qualification. The memory, process-count and individual-file limits have active OrbStack ARM64 checks; CPU quota has only been inspected, not stress-tested. Until the remaining integration and qualification work is complete, this foundation must not be advertised as complete isolated execution in the TUI.

The public HTTP runtime now streams worker stdout and stderr into `ExecutionEventBufferService`. Each event carries an execution ID, increasing sequence, stream and sanitized line. The buffer caps each line at 4 KiB, retains at most 2,000 output lines and 1 MiB (or the plan's smaller output limit), and emits a single truncation event. Docker drains later bytes without retaining them or terminating the worker. Infra commands keep their separate fatal output limit. The broker's `/v1/events` endpoint serves at most ten events per response after checking the caller's execution ownership; authenticated plans and runtimes without an event reader fail closed. The client verifies IDs, contiguous sequences, streams, content and response size. These events are currently memory held, so a broker restart yields a durable outcome but no replayable log. Session log import, artifact slots and broker bootstrap remain future work; public worker output can still contain arbitrary target text and must never be treated as instructions.

The broker also exposes owner-checked `/v1/cancel` and `/v1/renew` operations for a started run. Cancellation marks the stop reason and aborts execution, then returns the current state with cleanup still pending; it does not claim that the environment has already been removed. Callers must poll the durable receipt for confirmed cleanup. Renewal extends only the short ownership lease within the original absolute deadline, and cannot revive a stopped run. Neither operation invokes `start` or replays a scanner. The client validates the control response and fails closed on malformed data. These routes are not yet wired into the TUI because the broker daemon and application integration are still pending.
