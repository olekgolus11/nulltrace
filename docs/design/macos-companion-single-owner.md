# macOS companion single-owner prerequisite

Status: implemented as a native package prerequisite; not activated or security-qualified.

`CredentialCompanionOwnership` is the production gate for constructing a Keychain-backed credential record store. It derives one fixed owner-only root below the current user's Application Support directory and a fixed lock file below the installation namespace. Production callers provide only the namespace returned by the future trusted enrollment boundary. Test code alone can inject a temporary root.

Acquisition uses `open`/`openat` with no-follow flags, checks directory ownership and modes, checks that the lock is a current-user regular file with mode 0600 and one link, and takes a nonblocking exclusive `flock`. The open descriptors stay alive for the ownership object's lifetime, so process termination releases the kernel lock. The ownership object's mutex covers the full record read/compare/write transaction across every store using that object. Each Keychain backend operation rechecks that the root path, installation directory name, and lock pathname still refer to their retained descriptors. A replaced path therefore makes existing stores return unavailable before touching the backend.

These checks provide cooperative single-owner enforcement among trusted helper processes. They do not authenticate a same-user process or make owner-controlled paths immutable against a hostile process with the same UID. Path identity checks detect observed replacement and fail closed; they are not a claim that a same-user attacker cannot race filesystem operations. The installation UUID only separates namespaces and is never proof of identity.

Synthetic tests cover two store actors racing the same expected generation, a second process failing to acquire the same installation lock, process-death release, independent locks for separate installation IDs, and replacement of the root, installation directory, or lock file. A test-only probe executable receives only temporary UUID/path fixtures and invokes no Keychain operation.

The next stage must establish both transport identities before starting any listener. A bounded design candidate is: trusted launcher performs local enrollment, supplies an enrollment-scoped bootstrap over a private inherited pipe, helper binds its identity to a protected key, and the application control plane pins that helper identity while the helper pins the enrolled application identity. After pairing, a narrowly routed loopback endpoint can use mutual TLS with ephemeral session credentials. A claimed UUID, loopback address, Docker route, or admin token alone cannot replace this handshake. This design note does not implement enrollment, a listener, TLS, a launcher, or a root UUID authentication shortcut.
