# Companion peer identity verification prerequisite

Status: implemented as an inactive native-library prerequisite; it does not activate a companion or complete issue #162.

`CredentialCompanionPeerVerificationPolicy` is an immutable policy that must be constructed by the future trusted enrollment boundary before untrusted peer certificate bytes are processed. It contains the exact SHA-256 fingerprint of the expected leaf certificate, the TLS peer role, the server's exact DNS/IP identity when checking a server, and one or more enrollment CA certificates in DER form. The policy rejects malformed or oversized anchors, malformed pins, invalid server-name syntax, and a pin that names an enrollment anchor itself. There is no system-root trust mode or root fallback.

`CredentialCompanionPeerVerifier` accepts only an ordered leaf-first DER chain. It bounds the chain to eight certificates, 512 KiB per certificate, and 2 MiB total before passing data to Security.framework. It rejects empty, malformed, and non-canonical DER. The verifier uses `SecPolicyCreateSSL(true, expectedHostname)` for a server peer and `SecPolicyCreateSSL(false, nil)` for a client peer. It sets only the enrollment anchors, disables system-anchor fallback, disables trust network fetching, and supplies an empty keychain search list so chain building cannot silently import ambient intermediates. Security.framework evaluates certificate signatures, validity, SSL role/EKU, and server name. The exact leaf DER is then SHA-256 hashed and compared with the enrollment pin. The public result has only fixed nonsecret outcomes: verified, invalid input, invalid certificate, or untrusted peer.

`SecTrustSetKeychains` is deprecated by Apple, but remains necessary for the current no-ambient-keychain-search policy because the documented default trust evaluation may search keychains for intermediates. The package therefore depends on this deprecated Security.framework API until a supported replacement provides the same restriction. The tests exercise the behavior on the current macOS test host; they do not establish a complete macOS-version matrix.

The enrollment pin and anchors are trust decisions. Their future caller must be the trusted launcher/enrollment path, which must not derive them from a claimed installation UUID, loopback location, HTTP request, or peer-controlled field. This library currently has no enrollment authority or launcher, so its public policy initializer cannot prove who supplied those values. Production use must preserve the trust boundary and construct the policy from authenticated enrollment state.

The tests use only generated synthetic public X.509 fixtures. They evaluate a valid chain under an enrollment CA, reject an unrelated enrollment CA, wrong pin, wrong server name, expired leaf, server-only certificate in the client role, client-only certificate in the server role, malformed/empty/oversized input, and malformed pin/anchor/name policy. No private key, Keychain item, user certificate, listener, TLS handshake, network endpoint, or credential is accessed.

This verifier evaluates candidate certificate material only. It does not establish that the process presenting the certificate possesses its private key; that proof happens only inside a future actual TLS handshake. Enrollment, protected private-key custody, both identity pins at a trusted launcher, a mutual-TLS transport, same-UID process isolation, listener lifecycle, packaging/signing, and application integration remain unimplemented and unqualified. The existing cooperative single-owner lock is not process authentication, and the installation UUID remains a namespace only.
