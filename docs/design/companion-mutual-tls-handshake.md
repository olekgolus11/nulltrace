# Companion mutual TLS handshake prerequisite

Status: inactive transport prerequisite. It is not a companion listener, enrollment flow, application protocol, credential broker, or completion of issue #162.

`CredentialCompanionMutualTLSConnector` is a bounded outbound client connector for a future enrolled helper. Its only network destination is `127.0.0.1` and it accepts a nonzero TCP port plus an already available `SecIdentity`, a bounded leaf-first local certificate chain, and an immutable peer policy. The local chain is limited to eight certificates, 512 KiB per certificate, and 2 MiB total. Its leaf must exactly match the certificate returned by `SecIdentityCopyCertificate`. The connector does not create, import, persist, or look up identities or private keys; callers remain responsible for obtaining the local identity from a trusted enrollment boundary.

The connector privately constructs `NWParameters` and does not expose a parameter override. It pins TLS to version 1.3, supplies the enrolled local identity and certificate chain, requires peer authentication, disables TLS resumption and tickets, disables both Network.framework and TCP Fast Open, and sets the SNI value only from the server-name field of the trusted server peer policy. The endpoint address is always `127.0.0.1`; it is never substituted for the TLS service identity. A client connector refuses client-role peer policies.

Network.framework's peer verification callback is fail-closed. It reads the presented peer certificate chain from connection metadata, caps the certificate count, checks each returned DER buffer's length before converting it to the verifier's retained `Data` inputs, and delegates trust decisions to `CredentialCompanionPeerVerifier`. The verifier applies explicit enrollment anchors, a mandatory exact leaf pin, chain validity and signatures, and the role-specific SSL policy. The callback has no caller-provided bypass, accepts no UUID or HTTP-derived trust values, and returns only success or failure. The TLS callback may execute more than once; each invocation uses immutable policy and settles its callback once.

`connect` owns connection setup until `.ready`, cancellation, failure, or a fixed eight-second handshake deadline. It returns an `NWConnection` only after the TLS handshake succeeds and resolves the peer certificate. After return, the caller owns cancellation, send/receive deadlines, message framing, byte limits, and connection lifetime; this package does not provide those controls or an application protocol. This SDK's Network.framework options do not expose a separate TLS early-data setter. Fast Open is disabled, and consumers must send no application data before `.ready`.

The tests generate public synthetic X.509 certificates and ephemeral private keys at runtime in a protected temporary directory, construct `SecIdentity` in memory without Keychain APIs, and remove the temporary files. They use a test-only listener bound exactly to IPv4 loopback. A positive test completes an actual TLS 1.3 mutual-authentication handshake, checks the negotiated protocol version, and transfers a nonsecret canary only after both sides are ready. Negative tests cover wrong server name, wrong server pin, wrong client pin, and missing client identity; the server does not reach ready or receive application data. Separate tests cover cancellation before connection start, cancellation during a held handshake, fixed handshake timeout, invalid port, and role mismatch. They do not access the user's Keychain or production credentials.

This is only a transport prerequisite. The package still has no trusted enrollment authority, private-key custody contract, companion executable, production listener, launcher-to-helper bootstrap, protocol framing, or app integration. The repository separately defines endpoint reservation and worker network-deny prerequisites in [the control endpoint reservation design](http-control-endpoint-reservations.md), but this connector is not wired to an actual companion endpoint tuple or launcher policy. Synthetic TLS proves the implementation's handshake behavior with generated test identities; it does not prove a production launcher supplied the identities or protect against a hostile process running as the same user. The peer verifier evaluates certificate data alone and cannot prove private-key possession; possession is established only by the actual TLS handshake. These changes do not authenticate the surrounding process, establish same-UID isolation, or complete issue #162.
