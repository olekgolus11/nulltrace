# HTTP isolation: enforcement and compatibility research

Research for [Establish HTTP egress enforcement and current-tool compatibility limits](https://github.com/olekgolus11/nulltrace/issues/142), 2026-09-19. Code baseline: `f6ef6e0b210f45a151db6e5ca0bb39a06913675d`. This is evidence for architecture decisions, not an implementation or a claim of tested containment. No container, firewall, scanner, or acceptance experiment was run.

## Conclusion and trust boundary

A fixed HTTP proxy plus an independently enforced worker network policy is a viable architecture candidate. Proxy environment variables alone are not containment. The worker must be unable to reach anything except its assigned proxy listener; the proxy must separately constrain upstream destinations. The worker must not control either policy. Deployment feasibility on Docker Desktop and OrbStack remains an experiment, not a documented guarantee.

Squid CONNECT controls a requested host and port but does not inspect tunneled content. It does not establish the inner scheme, method, path, browser resource type, headers, or credentials. CONNECT can carry arbitrary bidirectional TCP. Consequently, non-MITM Squid cannot independently enforce full HTTPS exact-origin credential semantics or browser request semantics. Retain those application controls as additional layers and state their trust assumptions explicitly. No TLS interception is selected by this research. [Squid HTTPS documentation](https://wiki.squid-cache.org/Features/HTTPS)

An approved destination can itself relay traffic or receive secrets a compromised authorized worker knows. Network isolation limits the worker's reachable endpoints; it does not guarantee that the authorized target is trustworthy or eliminate exfiltration to that target. A stronger secret-confidentiality guarantee against a compromised worker would require a distinct credential mediation design, not just redaction after execution.

## Concrete Playwright conflict requiring a decision

Today an image such as `https://unrelated.example/pixel?...` passes the resource-type policy without a pre-approved host list. Allowing all external asset hosts preserves that behavior but abandons a fixed network destination allowlist. Allowing only the testing origin changes existing rendering. Automatically trusting every hostname suggested by a hostile page also abandons meaningful preauthorization.

Even if asset hosts are explicitly approved, the independent CONNECT boundary cannot tell an image request from a fetch, a navigation, a WebSocket handshake, or an exfiltrating URL inside the same tunnel. Browser routing remains useful but is not an independent guarantee against browser/worker compromise. Possible decision directions are an approved auxiliary-host policy with clearly bounded guarantees, or a separately trusted resource mediation design. Neither is chosen here; do not remove asset support or introduce MITM implicitly.

The current Playwright consent remains session-scoped. This research does not enable OpenCode web access or alter scanner approvals. The user's separate per-call target-webfetch consent requirement is a constraint for any future activation, not authorization to enable a currently disabled path.

## Enforcement design constraints to carry forward

- Establish deny-by-default network policy before any untrusted process starts. Use a separate trusted provisioning boundary; never give scanner workers or NullTrace `CAP_NET_ADMIN`. Rules must cover worker egress and proxy upstream egress, including other containers and host gateways. `inet` nftables tables cover IPv4 and IPv6; chains, hooks and default drop must match the actual namespace topology. This is a design requirement inferred from the available primitives, not a tested ruleset. [nftables manual](https://netfilter.org/projects/nftables/manpage.html)
- Bind exact hostname, port and protocol intent to approved resolved addresses. Squid offers `dstdomain`, `dst`, `port`, `proto` and `method` ACLs; plain domain matching is insufficient to prevent rebinding. Its documented reverse lookup fallback for numeric destinations warrants explicit handling. Pin permitted resolutions per run or validate every resolver result and enforce the same addresses at upstream connection time. CNAME, multiple A/AAAA answers, TTL changes and IPv4-mapped IPv6 need tests. [Squid ACL reference](https://www.squid-cache.org/Doc/config/acl/)
- Worker DNS is unnecessary for a fixed-IP HTTP proxy if the proxy resolves targets. Block worker UDP/TCP 53 and alternate resolvers, including Docker embedded DNS. Custom Docker networks use an embedded DNS server; `internal` networking or omitted ports alone is not evidence that resolver/host paths are contained. [Docker networking](https://docs.docker.com/engine/network/)
- Default-block loopback, link-local, metadata endpoints, host gateways and private destinations unless an exact approved target mapping needs them. Mac localhost, LAN and VPN are explicitly supported requirements: blanket private-network rejection is not acceptable. The worker must not treat its own loopback as the Mac's localhost. Resolve host-service mapping in the desktop-runtime decision.
- Use independent per-run policy identity, no policy cross-contamination, and startup/restart failure closed. Do not place a runtime socket in workers. Proxy configuration is read-only to workers; proxy compromise must not grant unrestricted upstream connectivity.
- Emit policy decision, opaque run identifier and controlled destination identity, not arbitrary request URLs, headers or bodies. Squid log formats expose URL/header fields, so default access/debug/error logging must be audited for secret leakage. No claim that selecting one access-log format sanitizes all logs. [Squid logformat](https://www.squid-cache.org/Doc/config/logformat/)
- Preserve ADR 0004 and 0007. The current Nuclei file matches authority, while application code separately constrains scheme and redirects; its exact-origin comment is not a Squid guarantee. Inject only one run's secret file with restrictive permissions; never mount the parent `run-secrets`/application-data directory. Keep lifecycle cleanup and existing output/artifact redactors. [Secret preparation](https://github.com/olekgolus11/nulltrace/blob/f6ef6e0b210f45a151db6e5ca0bb39a06913675d/src/features/tool/nuclei/services/nuclei-authenticated-run.service.ts), [Secret File generation](https://github.com/olekgolus11/nulltrace/blob/f6ef6e0b210f45a151db6e5ca0bb39a06913675d/src/features/tool/nuclei/services/nuclei-authenticated-run.helpers.ts)

## Experiments required before a security claim

Run on pinned Docker Desktop and OrbStack versions, recording image digests, tool versions, rules and topology. Instrument approved server A and denied server B with independent request counters plus packet capture; reset counters between cases. Observe denied DNS at a controlled authoritative server as well.

| Experiment | Required evidence |
| --- | --- |
| Allowed HTTP/HTTPS request and each migrated tool | A receives expected request; existing NullTrace logs, status, findings/artifacts remain usable. |
| A redirects to B (hostname, IPv4, IPv6, port and scheme variants) | B receives zero requests; rejected SYN/connect traffic corroborates network prevention. A NullTrace error alone is insufficient. |
| Direct sockets, unset proxy, NO_PROXY, alternate proxy, QUIC/UDP, raw IPv4/IPv6 | No connection to B; firewall counters/capture show enforcement. Use malicious-worker fixture in addition to normal tool configuration. |
| UDP/TCP DNS, Docker resolver, DoH/DoT to unapproved endpoints; rebinding/CNAME/mixed A+AAAA | No unapproved DNS or endpoint contact. An approved HTTPS server acting as DoH cannot be distinguished by non-MITM CONNECT: record this limit. |
| Assets, fetch, iframe, popup, service worker, WebSocket, redirects to already approved asset host | Verify both retained browser behavior and independent boundary; record where only application policy enforces semantics. |
| Credential canaries | Exact-origin target sees intended credential; B sees zero requests; no canary in argv/env, persisted commands, tool/proxy/error logs or exported artifacts. Inspect on success, failure, cancellation and timeout. |
| Nuclei protocol/OAST corpus | Classify working, blocked and unsupported cases without interpreting blocked scans as clean results. Confirm no runtime updates and no unplanned service contacts. |
| Lifecycle and filesystem/resource isolation | Missing policy/proxy fails closed; startup race/restart/cancel/timeout leaves no worker or secret; host secret, DB and credential store inaccessible; independent CPU/memory/PID/time/file limits verified. |

Nmap is outside the HTTP-proxy profile: its separate IP/port/protocol policy and out-of-scope scan prevention require their own experiments. No HTTP result proves Nmap containment. No security acceptance tests are marked passing by this research.
