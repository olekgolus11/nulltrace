# Enforceable isolation on Docker Desktop and OrbStack

Research date: 2026-09-19. Decision ticket: [Establish enforceable isolation options on Docker Desktop and OrbStack](https://github.com/olekgolus11/nulltrace/issues/141).

This is documentary research, not an architecture decision or successful sandbox test. No containers, firewall changes, target requests, or resource-exhaustion experiments were run. Sources describe current documentation; a supported release must pin and test actual runtime versions.

## Scope and conclusion

The agreed destination is Docker Compose distribution on macOS with Docker Desktop and OrbStack, preserving current operator workflows and migrating tools separately. Public, Mac-local, LAN, and VPN targets are required. ADR 0002, 0004, and 0007 remain constraints: separate chat runtime, ephemeral Nuclei Secret Files, and authenticated exact-origin delivery.

The documented primitives can support a layered design, but do not prove a portable implementation. In particular, an internal Compose network is not sufficient proof of proxy-only access; rootless execution does not automatically enforce resource limits; and desktop networking does not guarantee every raw Nmap mode. These are experiments to resolve before selecting the infrastructure contract.

## Evidence matrix

| Area | Documented fact and primary source | Implication / unresolved question |
| --- | --- | --- |
| Docker authority | Docker daemon control permits powerful filesystem mounts; callers must be trusted. [Engine security](https://docs.docker.com/engine/security/) | A read-only socket mount is not a read-only Docker API. Candidate narrow broker must own immutable launch profiles and reject arbitrary mounts, images, network attachments, capabilities, and daemon options. Broker compromise remains a high-impact boundary. |
| macOS boundary | Desktop containers run in a Linux VM; container root and macOS root are distinct, and shared host directories remain accessible according to file-sharing permissions. [Mac permissions](https://docs.docker.com/desktop/setup/install/mac-permission-requirements/) | Do not call a Desktop installation “rootless Docker” just because the Mac application runs as an ordinary user. Protect NullTrace volumes independently of the VM boundary. |
| Rootless alternative | Rootless runs daemon and containers inside a user namespace. [Rootless mode](https://docs.docker.com/engine/security/rootless/) CPU/memory/PID flags require cgroup v2 and systemd; missing prerequisites can make flags ignored. Documented nested rootless Docker requires a privileged parent. [Rootless tips](https://docs.docker.com/engine/security/rootless/tips/) | Compare a broker against a separately provisioned rootless engine; neither has been selected. Nesting is not an automatic least-privilege solution. Verify effective cgroups, not only requested flags. |
| Worker filesystem and process | Docker exposes non-root UID, read-only rootfs, capability removal, security options, PID limits, ulimits, tmpfs and explicit cleanup. [Run reference](https://docs.docker.com/reference/cli/docker/container/run/) Tmpfs may reach swap. [Tmpfs mounts](https://docs.docker.com/engine/storage/tmpfs/) | Candidate profile: no-new-privileges, no inherited environment, no host/app/socket mounts, bounded scratch space and independent deadline controller. Tmpfs is not proof that a secret never touches disk. A per-file size limit is not an aggregate scratch-space limit. |
| CPU and memory | Containers have no resource constraints by default; Docker provides hard memory and CPU limits with host support. [Resource constraints](https://docs.docker.com/engine/containers/resource_constraints/) | Observe OOM, fork-limit and CPU throttling under each desktop runtime. Main-process cancellation alone does not bound orphaned workers. |
| Seccomp and LSM | Seccomp needs kernel/runtime support and has a default allowlist. [Seccomp](https://docs.docker.com/engine/security/seccomp/) AppArmor requires a loaded enforcing policy. [AppArmor](https://docs.docker.com/engine/security/apparmor/) | Pin profiles, inspect effective enforcement, and run denied operations. Desktop/OrbStack AppArmor or SELinux availability is unverified; absence must be explicit in the support policy. Never silently use unconfined execution. |
| Internal network | Internal networks still allow same-network peers and the gateway, including appropriately bound host services. [Network creation](https://docs.docker.com/reference/cli/docker/network/create/#network-internal-mode---internal) | A worker-plus-proxy bridge needs additional prevention of gateway/peer access. No evidence yet that internal networking alone meets the requirement. |
| DNS and namespaces | Custom networks use embedded DNS at `127.0.0.11`, forwarding external queries. Containers can share another container's network namespace; that mode restricts DNS-related launch options. [Networking overview](https://docs.docker.com/engine/network/) | Explicitly test embedded DNS, direct UDP/TCP DNS, IPv6, and alternate resolvers. A candidate namespace initializer must install policy before worker start, without exposing a privileged controller to worker traffic. |
| Firewall placement | Docker's nftables backend is documented as experimental; it owns its tables, and has no `DOCKER-USER` chain. [Docker nftables](https://docs.docker.com/engine/network/firewall-nftables/) | Do not assume Linux-host iptables recipes map to the desktop VM. Compare namespace-local filtering and a separate gateway; avoid changing shared engine rules. The helper's authority and policy-installation race require experiments. |
| HTTP proxy | Squid supports destination, domain, port, protocol and method ACLs with ordered access rules. [ACLs](https://www.squid-cache.org/Doc/config/acl/), [HTTP access](https://www.squid-cache.org/Doc/config/http_access/) Its configurable log fields can include URLs and headers. [Log format](https://www.squid-cache.org/Doc/config/logformat/) | Candidate: worker can reach only the proxy; proxy policy independently constrains destinations. Audit only bounded allow/deny metadata, omitting URLs, queries and headers. HTTPS tunnel permission alone cannot enforce credential-bearing HTTP paths or headers; no TLS interception is proposed. |
| Desktop destinations | `host.docker.internal` reaches Mac services; Desktop supports VPN networking. [Desktop networking](https://docs.docker.com/desktop/features/networking/networking-how-tos/) | Localhost must have explicit routing semantics while preserving the operator-approved origin, HTTP Host, SNI, and certificate checks. Test split DNS/VPN transitions; support claims are not tests of every corporate VPN. |
| OrbStack destinations | OrbStack documents Mac access, VPN/DNS integration, system proxies, direct container-IP access, and optional IPv6. [Container networking](https://docs.orbstack.dev/docker/network) | Test separately from Desktop, including proxy exclusions, IPv6 enabled, and host-service exposure. Transparent upstream proxies alter the traffic path; do not confuse them with NullTrace's enforcement proxy. |
| Nmap | Nmap proxy support excludes ordinary port scanning, host discovery and OS discovery. [Nmap proxy limitations](https://nmap.org/book/man-bypass-firewalls-ids.html) TCP connect scanning works without raw-packet privilege. [Scan techniques](https://nmap.org/book/man-port-scanning-techniques.html) Desktop host networking supports only layer 4 protocols and does not expose host interfaces. [Host networking](https://docs.docker.com/engine/network/drivers/host/) | Nmap needs its own IP/port/protocol policy. Raw mode capabilities and actual packet behavior must be demonstrated on both products. Granting NET_RAW does not prove Mac LAN raw-packet equivalence; host networking is not a safe workaround. |

## Candidate approaches to compare, not decisions

1. A narrowly scoped broker controlling per-run workers through the existing engine, plus a per-run network enforcement component. Simple packaging may trade against the broker's broad daemon authority.
2. A dedicated rootless execution engine with verified cgroup delegation and networking. Reduced daemon authority may require extra provisioning incompatible with a simple Compose installation.
3. For the network component, compare a prepared worker namespace with a separate filtering gateway. HTTP proxy and raw Nmap paths need different policies. With NET_RAW, include raw Ethernet/packet sockets and bridge paths in enforcement tests, rather than assuming ordinary IP output rules cover every packet.

The app and workers must not obtain network-administration authority. Any administrative setup belongs to the minimal infrastructure component. Control-plane ports and policy files must be unreachable from workers. These are constraints from the requested threat model, not claims that either candidate already satisfies them.

## Decisive experiment checklist

Run against recorded Desktop and OrbStack versions; retain image digests, architecture, engine/Compose versions, effective security options, rulesets and sanitized captures.

1. **Enforcement readiness:** verify UID, effective capabilities, no-new-privileges, seccomp, LSM availability and cgroup controllers. Start an immediate-connect worker while delaying policy installation; it must have no open network window. Killing the controller must not open traffic.
2. **Allowed destinations:** exercise public, Mac-loopback-bound, LAN and VPN fixtures, with split DNS and both IP families where supported. Verify original origin/Host/SNI and TLS semantics, including authenticated requests, without broad host access exceptions.
3. **Pre-send denial:** an allowed fixture redirects to an outside fixture with a server-side request counter. Counter must remain zero. Repeat with direct IPv4/IPv6, literals, alternate ports, `NO_PROXY`, Docker gateway, metadata/link-local addresses and sibling services. Capture denied destination traffic, not just client error strings.
4. **DNS/tunnel bypasses:** query controlled authoritative DNS through embedded DNS, direct TCP/UDP 53, alternate resolvers and DoH. Attempt CONNECT to unauthorized hosts/ports, DNS rebinding between approval and connect, WebSocket and QUIC routes. Require resolver counters and packet evidence of denied attempts. Specify residual risk of tunneling through an authorized application.
5. **Authority and secrets:** canary files in Mac home, app database volume and credential store must be unreadable; broker/socket and policy mutation must be inaccessible. Inject dummy credentials and inspect process args/env, worker/proxy/runtime logs and returned artifacts. Check secret-file UID/mode and destruction on every exit path.
6. **Bounds and lifecycle:** demonstrate memory/PID limits, CPU throttling, file/scratch/output limits, wall-clock timeout, cancellation, app/broker crash and runtime restart. Verify no orphan containers/networks/secret volumes remain after recovery; enumerate rather than assume `--rm` handles everything.
7. **Nmap fidelity:** an authorized fixture receives the expected connect/raw probes; forbidden IPs and ports receive none. Compare packets for discovery, SYN, UDP and OS modes against a reference, including raw packet/fragment/IPv6 paths. Record unsupported modes instead of switching silently to unrestricted execution.
8. **NullTrace compatibility:** the first migrated tool retains history, bounded logs, sanitized artifacts and findings persistence. Browser tests also cover cross-origin subresources, downloads, service workers, popup and WebSocket behavior. OpenCode research traffic remains a separate policy.

## Handoff

Documentation identifies viable primitives and concrete gaps; it does not establish that out-of-scope traffic is prevented. Selecting a topology and claiming support requires the experiments above. No application code changed and no unit, integration, or type-check suite was run for this documentation-only investigation.
