# macOS credential companion foundation

This package implements a small internal target-context credential-record layer for a future user-level macOS companion. It uses generic-password items through Security.framework and exposes only typed record kinds, UUID record IDs, schema version 1, bounded JSON payloads, and expected-generation save/delete operations. The Security backend derives separate account namespaces for target context, provider login, and raw-evidence-key kinds. Only target-context payloads are currently accepted; provider and evidence payload integration is not implemented. Reads never enumerate Keychain items or accept a caller-provided Keychain service/account/query.

Target payloads require a normalized HTTP(S) origin with a canonical hostname or IPv6 literal and a valid explicit port. They accept bounded cookie, header, and browser-storage maps. Header and cookie names must use RFC token characters; header values and cookie paths reject control characters, cookie values use the RFC cookie-octet subset, cookie booleans and expiry values have exact JSON types and bounded ranges, and cookie domains must match the origin host. Empty hosts, noncanonical origins, unknown fields, and unknown schemas are rejected. Loopback reachability is not evaluated here and must be controlled by the authenticated operation's network policy. The helper-owned Keychain envelope stores a monotonically increasing generation and a deletion tombstone. Delete overwrites the record payload with the tombstone; it does not call `SecItemDelete` and makes no claim about physical erasure. A stale write cannot recreate the cleared payload. Failures distinguish invalid input, conflict, not-found, unavailable/locked, denied, corrupt data, and other backend errors without including record contents. Encoded records are size-checked before decoding.

The package has no companion executable, listener, enrollment protocol, application identity source, authenticated transport, or launcher. Production Keychain store construction now requires a live `CredentialCompanionOwnership` guard. The guard takes a nonblocking `flock` on a fixed per-installation lock file below the companion's fixed Application Support root. It validates owner-only directory and file modes, rejects symlink and hard-link lock files, retains the lock descriptor for process lifetime, and checks that the named root, installation directory, and lock file still identify the held descriptors before every backend operation. The guard's recursive mutex spans the entire read/check/write transaction across every store instance that shares it. A process crash releases the kernel lock; no stale PID cleanup is needed.

Custom lock roots exist only as an internal test seam. Production callers cannot choose another root for the same installation namespace. The namespace is supplied by the future trusted enrollment boundary; it does not authenticate a process or authorize a caller. `flock` is cooperative single-owner enforcement for trusted helper processes. A hostile process running as the same user can replace owner-controlled filesystem paths, so path identity checks fail closed when replacement is observed but do not establish a distinct OS principal or defeat every malicious same-user race. The guard serializes CAS for stores sharing its ownership instance and prevents a second helper process from taking the same fixed installation lock; it is not a substitute for authenticated transport or OS-level identity separation.

Authenticated encrypted transport, mutual identity verification, enrollment, packaging/signing, and application adapter work remain prerequisites to activation. The companion must not open its listener before a trusted enrollment flow establishes both identities. A concrete next design is to have the trusted launcher transfer an enrollment-scoped bootstrap through a private inherited pipe, bind the helper identity to a protected key, and then establish mutually authenticated TLS with pinned identities and ephemeral session credentials. The installation UUID remains a namespace only. No listener, bootstrap secret channel, TLS endpoint, or pairing shortcut is implemented here.

The standalone `CredentialCompanionPeerVerifier` prerequisite verifies a bounded, leaf-first certificate chain against explicit enrollment CA anchors, an exact leaf SHA-256 pin, and a role-specific SSL policy. It never falls back to system roots. It disables network trust fetching and uses the deprecated `SecTrustSetKeychains` API with an empty search list to prevent ambient intermediate-certificate lookup; this behavior needs qualification across supported macOS releases. The verifier evaluates candidate certificate material only: it does not prove TLS private-key possession, perform trusted enrollment, establish process identity or same-UID separation, or activate mutual TLS. Its enrollment pin and anchors are safe to use only when supplied by the future trusted launcher, never from a claimed installation UUID, loopback address, or HTTP payload. See [the peer identity verification design](../../docs/design/companion-peer-identity-verification.md) for the API contract, bounds, tests, and assurance limits.

Tests inject an in-memory backend containing synthetic values. A small test-only process probe exercises competing ownership and process-death release; neither test path constructs the Keychain backend. Tests do not access the user's Keychain or credentials. The package is a bounded implementation prerequisite, not a security qualification or completion of issue #162.

Run checks on macOS with:

```sh
swift test
swift build
```
